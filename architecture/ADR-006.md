# ADR-006 — Assignment lifecycle: no hard delete + in-place correction

> Architect decision 2026-07-30 · PACK-002 dry-run corrections

## Context

PACK-001 FKs use `vehicle_assignments.vehicle_id … ON DELETE CASCADE`. Hard DELETE of vehicles (or assignments) destroys historical attribution. Dry-run required a single authoritative correction workflow.

## Decision 1 — No hard delete in normal PACK-002 behavior

| Record | Active | Ended / inactive | Representation |
|---|---|---|---|
| Assignment | `valid_until IS NULL` OR `valid_until >= today` (ops view) / as-of match for history | **Ended:** `valid_until` set to last inclusive day | Row **retained forever** in normal product paths |
| Vehicle / driver / customer | `active = true` | `active = false` (deactivated) | Row retained; no product DELETE |

- **Close/end assignment:** `UPDATE` sets `valid_until` only; never `DELETE FROM vehicle_assignments`.
- **Deactivate master:** `UPDATE … SET active = false`.
- **Cascade protection:** PACK-002 Apply migration **must** change `vehicle_assignments.vehicle_id` FK from `ON DELETE CASCADE` to **`ON DELETE RESTRICT`** so accidental SQL/admin deletes cannot wipe history. Driver/customer FKs remain `ON DELETE SET NULL` (nulls attribution, does not remove rows) — still prefer deactivate in product UI.
- **Exceptional administrative cleanup** (DBA SQL, legal purge): **out of PACK-002 scope**; not exposed in product UI/API.

## Decision 2 — Authoritative correction method: **A — safe in-place update**

Selected: **Option A** — correct an existing assignment with a **single-row `UPDATE` inside one database transaction**.

**Not selected:** Option B (close + create replacement) as the correction path. Splitting/replacing periods is done only via explicit **End** then **Create** user actions (two approved operations), not as silent Builder choice inside “correct”.

### Correction transaction rules

1. Begin transaction.
2. Lock or re-read target row (`SELECT … FOR UPDATE` recommended).
3. Apply proposed field changes (`valid_from`, `valid_until`, `driver_id`, `customer_id`, `notes`, etc.).
4. Enforce FR-002-05 (≥1 of driver/customer) and period CHECK.
5. Re-validate overlap against **all other** rows for the same `vehicle_id` (exclude self).
6. `UPDATE` the row; DB exclusion constraint re-checks under concurrency.
7. Commit. On any validation/DB overlap failure → **full rollback**.

### Conflict

- HTTP **409**, `code`: **`ASSIGNMENT_OVERLAP`**

### Open-ended periods

- `valid_until = NULL` means unbounded end; correcting to a finite end is allowed if the resulting set is non-overlapping.
- Opening an ended row (`valid_until` → `NULL`) is an in-place correction and must pass the same overlap check.

### Correcting start, end, or masters

| Change | Behavior |
|---|---|
| `valid_from` / `valid_until` | In-place; full overlap re-check |
| `driver_id` / `customer_id` | In-place; must keep ≥1 party |
| `notes` | In-place; no overlap impact |
| Failure mid-flight | Transaction abort; no partial write |

## Status

**ACCEPTED** for PACK-002.
