# Requirements — Fleet Utilization Reports (FUR-001)

> Generated by Project Launcher Pro v4.4.1 on 7/29/2026
> Fachquelle: `Anweisungen die Cursor in Project launcher eintragen soll.txt`

## One-liner

Internes Fahrzeugauslastungs-Reporting: Frotcom-Tagesdaten speichern, zuordnen, auswerten und für Manager exportieren.

## Problem

Manager fehlen prüfbare historische Berichte über Fahrzeugnutzung (Kilometer, Fahrzeit, Standzeit, Fahrer, Auftraggeber, Start-/Endort) mit konfigurierbaren Zielstatus — ohne Frotcom als TMS zu ersetzen.

## Business outcome

Tägliche und historische Auslastung ist im Dashboard filterbar sichtbar; Zuordnungen sind zeitabhängig; Excel/PDF-Exporte spiegeln Filter; Sync läuft geplant über n8n; keine Live-Neuziehung der gesamten Frotcom-Historie bei jedem UI-Aufruf.

## Target users and roles

- admin — Stammdaten, Zuweisungen, Imports, Einstellungen, Korrekturen
- manager — Berichte, Filter, Exporte, Details
- viewer — nur Lesen

Zielgruppe: internes Management einer Spedition.

## Current workflow

Nutzungsdaten liegen in Frotcom; Zuordnungen und Managementberichte sind heute nicht als konsistentes, historisches internes Reporting-Tool abgebildet. [OFFEN: exakter Ist-Prozess vor Ort — ASM dokumentiert]

## Data sources

- Primär: Frotcom API (Fahrzeuge, Tagesaktivität, ggf. Fahrer/Tachograph)
- Persistenz: Supabase / PostgreSQL
- Orchestrierung: n8n (täglicher Import Vortag)
- Manuell/Excel: Fahrer- und Auftraggeberzuweisungen

## Business rules

- Ein Tagesbericht pro Fahrzeug und Berichtstag; Upsert idempotent
- Status aus konfigurierbaren Fahrzeit-Schwellen (Standard: ≥9h ok; 7–8:59h prüfen; 0:01–6:59h stark unter Ziel; 0 km / keine Bewegung = nicht eingesetzt)
- Standzeit MVP = Fenster erste–letzte Bewegung minus Fahrzeug-Fahrzeit
- Rohzeiten UTC speichern; Aggregation in konfigurierbarer Betriebszeitzone
- Historische Zuordnung am Berichtstag, nicht die heute aktuelle
- Fahreranzeige-Priorität: Frotcom/Tacho (wenn verlässlich) → manuelle/importierte Zuweisung → „nicht zugewiesen“
- Kilometer-Quellenreihenfolge: offizieller Tages-/Tripwert → Odometer Ende−Beginn → Telematik → GPS nur als gekennzeichneter Fallback
- Keine Service-Role-Keys im Browser; RLS nach Rolle

## Edge cases and risks

- Teilfehler einzelner Fahrzeuge dürfen den Gesamtsync nicht vernichten
- Doppelimporte müssen idempotent bleiben
- Überlappende Zuordnungen erkennen
- Suspicious data quality sichtbar kennzeichnen (negative km, End vor Start, …)
- Chat-geleakte Credentials sind kompromittiert und unbrauchbar

## Constraints

- Kleines internes Tool; kein SaaS-Mehrmandant
- Keine erfundenen Frotcom-Endpunkte
- Keine Secrets in Repo
- Stack-Präferenz: Next.js App Router, TypeScript strict, Supabase, n8n, server-seitige Exporte

## Existing tools and integrations

Frotcom (Telematik), geplante n8n-Workflows, Supabase Auth/DB. [OFFEN: konkrete Frotcom-Vertragsdetails]

## Acceptance criteria

- Manager sieht gefilterte Tages-/Zeitraumübersicht mit Status und Kennzahlen
- Fahrzeugdetail mit Tageszeilen und historischen Zuordnungen
- Stammdaten + zeitabhängige Zuweisungen + Excel-Import mit Vorschau/Konflikten
- Exporte Excel/PDF respektieren Filter
- Täglicher Sync schreibt idempotent in DB; Dashboard liest aus DB
- Rollen admin/manager/viewer mit RLS
- Tests für Aggregation, Zeitzone, Status, Zuordnungen, Import, Sync-Teilfehler (siehe `quality/TEST-MATRIX.md`)

## Non-goals (MVP)

Vollständige Live-Karte/Routen, Tourenplanung, Auftragsdisposition, Rechnung, Lohn, gesetzliche Tacho-Bewertung, KI, Fahrer-App, Kundenportal, Mehrmandantenfähigkeit, vollständiges TMS.
